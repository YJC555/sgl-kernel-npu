A3 分层通信：方案 A（AI-RMA QP）与方案 B（窗口直写）

本文说明 A3（910_93）双机 32 卡 layered dispatch 在 stage 6/7 挂死的原因，对比“AIV 核直接发 RoCE WQE”与“直接写对端窗口”两条数据面实现， 并解释为什么 A5 可行、A3 不可行，以及窗口直写在跨节点场景下为什么依然有效。

结论一

方案 A 在 A3 不可用

HcclEngineCtxGet(..., COMM_ENGINE_AIV, ...) 在 910_93 返回 HCCL_E_PARA(1)，HCCL 不会向 MC2 算子下发 aiRMAInfo（QP 表），kernel 侧无 WQE 可拼。

结论二

方案 B 可落地且语义等价

把“发 RDMA WQE”换成“写 WindowIn(peer) 窗口地址 + flag”。接收侧代码零改动，先 payload 后 flag 的可见性语义与原设计一致。

结论三

算法与拓扑不变

14 个阶段、本地聚合（stage 7）、server 内扇出、ack 回传全部保留；A5 路径零影响。变化只发生在“最后一公里”的搬运指令。

1. 问题现象与定位结论

1.1 现象

A3 双机（2 × 16 卡，共 32 卡）运行 layered dispatch，notify 算子卡在 stage 6 / stage 7：

  • 主节点：AIV0 打出 701 → 703 → 704 → 702 → stage 7，AIV1 只打出 701 后停住；
  • 从节点：现象相反（AIV1 走完全程，AIV0 停在 701）；
  • 两台机器的其余核卡在 StageBoundary(7) 的 SyncAll，互相等待，进程挂死。

1.2 日志证据

[ln] ctx sz=32 winMB=3000 localIn=80000000
[ln] ctx same r=0  ptr=c1faf000 win=0
[ln] ctx peer r=31 ptr=c05f8000 win=80000000   <-- 对端窗口地址正常
[ln] tp 703 aiv 1 v 31
[ln] ctl self=1 proxy=31 rps=16 inSrv=1
[ln] qp dst=31 info=0 num=0 size=0 addr=0          <-- QP 描述符为空

窗口侧（WindowIn）全部正常，唯一缺口是 context_->aiRMAInfo == 0，即 MC2 算子的 op param 里没有 AI-RMA 的 QP 表。

A3 分支的 PostRdmaSend 第一句就是 rdmaInfo_->qpNum，空指针解引用后该 AIV 核直接 trap，所以 704/702 不再出现，另一核卡在 SyncAll。

定位结论：stage 6 的“跨节点发送核”在 PostRdmaSend 之前就异常退出，导致 stage 7 的 SyncAll 永远无法收敛。根因不是算法，也不是窗口，而是 QP 表缺失。

3. 为什么方案 A 在 A3 不行

3.1 方案 A 的完整链路

图 1　方案 A：QP 表由 HCCL 在 AIV 引擎上下文建立后下发，kernel 据此直接提单

3.2 仓库里这段代码在哪

  • tiling 侧已声明要 AIV 引擎：notify_dispatch_normal_layered_tiling.cc 中 Mc2CcTilingConfig(...) + SetCommEngine(mc2tiling::AIV_ENGINE)。
  • host 侧负责“把引擎建起来”：cam_moe_layered_comm_context.cpp，链路为 HcclCommMemReg → HcclChannelAcquire(COMM_ENGINE_AIV) → HcclEngineCtxCreate(COMM_ENGINE_AIV)。原本整段被 #if defined(__DAV_C310__) 限制为 A5 专用。
  • kernel 侧读取：cam_moe_layered_comm.h 中 rdmaInfo_ = (__gm__ HcclAiRMAInfo *)context_->aiRMAInfo;，随后在 PostRdmaSend 里按 dstRank 定位 SQ、构造 WQE。

3.3 实测结果

把 host 侧 arch 门控去掉，按 A5 完全相同的逻辑在 A3 上执行，第一处 HCCL 调用就被拒绝：

// cam_moe_layered_comm_context.cpp: GetExistingEngineContext
ret = HcclEngineCtxGet(comm, contextTag.c_str(), CommEngine::COMM_ENGINE_AIV, &engineContext, &contextBytes);
if (ret != HCCL_SUCCESS && ret != HCCL_E_NOT_FOUND) {
    HostTrace("fail step=engine-get code=%d", static_cast<int>(ret));
    return ret;
}
// 输出：fail step=engine-get code=1
要点：正常语义下“上下文尚未创建”应返回 HCCL_E_NOT_FOUND，代码会继续走创建流程； 但 A3 返回的是 HCCL_E_PARA(1)，属于“引擎类型不支持”的硬错误。这说明 910_93 的 HCCL 不提供 COMM_ENGINE_AIV， 自然不会向 op param 写 aiRMAInfo。

还有一个反证：kernel 里 A3 的 AI-RMA 分支是完整实现的（PostRdmaSend 的 #ifndef __DAV_C310__ 分支，注释写作 “A3 AiRMA RDMA write”），说明代码作者原意是 A3 也能用。缺的不是 kernel 逻辑，而是平台侧能力。

4. 为什么方案 B 可以

4.1 核心：窗口地址本身就是“远端可写地址”

A3 的通信窗口由 HCCL 注册（HcclCommMemReg + rank graph 建链），注册后每个 rank 拿到的 remoteRes[peer].nextDevicePtr->windowsIn 是统一地址空间里的远端窗口地址：

  • 同一 server 内 → 该地址映射到对端 HBM，硬件走 HCCS；
  • 跨 server → 该地址由 HCCL 传输层接管，落到该地址的写会被封装成 RDMA 写发到对端。

因此 kernel 只需要“往这个地址写数据”，不需要知道 QP、SQ、mem key——拼包这件事由 HCCL 内部完成。

图 2　方案 B：kernel 直接写远端窗口地址，由 HCCL 传输层按拓扑选择 HCCS 或 RoCE

4.2 为什么语义等价

方案 A 的两次 WQE 做的事情是：把 src 的数据放进远端 dst 这块内存，然后再写一个 flag。方案 B 做的是完全相同的一件事，只是把“网卡异步搬”换成“核自己搬”。接收侧代码完全不知道区别：

// 接收侧（未改动）
Wait((__gm__ uint64_t *)(in + flag), ComposeFlag(epoch, Phase::CONTROL_COUNT_READY));
cacheReadInvalidate(in + ControlLaneOffset(...), layout_.controlStride);

正确性依赖两点，方案 B 都满足：

  1. 顺序：先 payload、后 flag（代码里两段之间还有 TracePoint(704)，便于确认）；
  2. 可见性：写 flag 前有 MTE3_S 同步，对端读数据前有 cacheReadInvalidate。

4.3 仓库内的既有佐证

A3 的非分层路径（moe_distribute_dispatch_v2、moe_distribute_combine_v2、cam_moe_combine_normal_multi_round）在 32 卡跨 2 台的 ep 域上，全部使用 GetBaseWindAddrByRankId + DataCopyPad 写远端窗口 + flag 的方式，从未使用 aiRMAInfo。方案 B 只是把 layered notify 也拉回同一套机制。

5. A5 支持、A3 不支持的原因

维度A5（C310 / 950）A3（910_93）
宏__DAV_C310__ 已定义未定义，走 SocVersion::ASCEND910_93
数据面机制hcomm 通道 + AIV 引擎上下文（CANN 9.2+）HCCL 窗口（HCCS / RoCE 由传输层调度）
kernel 提单能力可以：AIV 直接操作 HW channel，发 WR不可以：无 AI-RMA 能力，SQ 未暴露给 AIV
COMM_ENGINE_AIV支持，HcclEngineCtxCreate 成功不支持，HcclEngineCtxGet 返回 HCCL_E_PARA
aiRMAInfo由 HCCL 填充恒为 0

这是平台能力差异，不是配置差异：A5 的软硬栈把“AIV 直接驱动网卡队列”的能力开放给了 kernel；A3 的 RoCE 仍由 HCCL 自己驱动，应用层拿不到 SQ 描述，也无法自行创建 QP（没有 verbs 接口）。

表述建议：对外说明时不要写“QP 专属 A5”。准确说法是——在 A3(910_93) 与当前 CANN 版本上，HCCL 不提供 COMM_ENGINE_AIV（返回 HCCL_E_PARA），因此不会下发 aiRMAInfo。若后续 CANN 在 A3 上支持该引擎，改回两处开关即可复用方案 A。

6. 关键问答：DataCopy 走的是 RoCE 而不是 HCCS，为什么能用

Q：跨节点没有 HCCS 直连，DataCopy 是一条本地拷贝指令，凭什么能写到另一台机器？

A：因为它写的不是普通 HBM 地址，而是 HCCL 窗口地址。

拆成三层看：

6.1 地址层：这个 VA 是 HCCL 分配的

WindowIn(peer) 来自 remoteRes[peer].nextDevicePtr->windowsIn。这个值在 HcclCommMemReg 注册窗口、rank graph 建立链路时由 HCCL 分配，是统一编址空间里的地址，不是对端 HBM 的物理地址。AIV 写它时，硬件看到的是一条“窗口地址写”，由地址解码交给传输层。

6.2 传输层：谁把数据送过网

跨节点的窗口写，最终仍然由 RoCE 网卡发出，但“拼 RoCE 包”的主体是 HCCL 的传输层（它内部持有这些 QP），不是 AIV 核。这与方案 A 的差别只在于：

方案 A方案 B
谁拼 WQE / 网络包kernelHCCL 传输层
kernel 需要什么QP 号、SQ 地址、mem key（aiRMAInfo）只需要目标窗口地址
物理介质RoCERoCE（跨节点）/ HCCS（同节点）

换句话说：两条路都过 RoCE，区别是“谁提单”。方案 A 把提单权交给了 kernel（因此需要 QP 表），方案 B 把提单权留给 HCCL（因此不需要 QP 表）。

6.3 语义层：为什么“写内存”等价于“发消息”

  • 窗口注册时，双方约定了窗口大小与地址映射，任何一方写 peer.windowsIn + off 都等同于写对端 HBM 的对应位置；
  • flag 也是同一块窗口里的一个槽位，所以“写数据 + 写 flag”天然有序且可被对端轮询到；
  • 对端Wait 轮询的是自己的窗口（本地地址），看到 flag 后 cacheReadInvalidate 再读 payload，读到的一定是最新值。
一句话总结：方案 B 并没有“绕开网络”，它把“发包”的职责从 kernel 交回给 HCCL。因此不需要 aiRMAInfo，也没有“没有 QP 就无法通信”的问题。

6.4 与同节点窗口直写的区别

你会注意到日志里同节点 peer 的 windowsIn 打出来是 0（例如 ctx same r=0 ptr=c1faf000 win=0），这是该 relation 结构的字段在该部署下未填充，不代表同节点不可写——同节点的数据面在本仓库走的是另一条既定路径（写本 rank 窗口后由 owner 处理）。跨节点方向观测到的 win=0x80000000 才是本次发送实际使用的地址。

7. 方案 B 的具体实现

7.1 改动清单（提交 6f10fc4，分支 a5_layered）

文件改动
deep_ep.cppAIV 引擎上下文只在 A5(ASCEND950) 创建；A3 不再尝试，避免 Buffer 构造期抛异常，roceContext 回到 dummy 张量（A3 kernel 不使用它）。
cam_moe_layered_comm.h新增 DirectWindowWrite()：A3 返回 true，A5 返回 false，作为选择分支的单一开关。
notify_dispatch_normal_layered.cppstage 6 的 count payload / flag、stage 12 的 base ack payload / flag 共 4 处，在 A3 上改走已有的 CopyWindowBytes / CopyWindowFlag。
A5 全路径零改动，仍走 hcomm 通道 + PostRdmaSend。

7.2 发送分支的写法

// stage 6：发布 count 控制信息
if (proxyRank == info_.epRankId || comm_.DirectWindowWrite()) {
    // A3：直接写到对端窗口（或本地窗口）
    CopyWindowBytes(payload, dst, layout_.controlStride);
} else {
    // A5：AI-RMA 提交 WQE
    comm_.PostRdmaSend(payload, dst, proxyRank, layout_.controlStride, *doorbell_, *head_);
}
CopyWindowFlag(dst, layout_.countFlagOffset, ComposeFlag(epoch, Phase::CONTROL_COUNT_READY));

7.3 搬运实现

// CopyWindowBytes：分块 GM → UB → 远端窗口 GM
for (uint64_t offset = 0U; offset < bytes; offset += kAggregateCopyTileBytes) {
    const uint64_t left = bytes - offset;
    const uint64_t tile = left < kAggregateCopyTileBytes ? left : kAggregateCopyTileBytes;
    DataCopyPad(ub, src + offset, ...);        // MTE2：本地 GM → UB
    SyncFunc<MTE2_V>();
    DataCopyPad(dst + offset, ub, ...);        // MTE3：UB → 远端窗口
    SyncFunc<MTE3_S>();
}

// CopyWindowFlag：8 字节 flag 写到远端窗口的 flag 槽
DataCopyPad(flagUb, value, ...);
SyncFunc<MTE2_V>();
DataCopyPad(dst + flagOffset, flagUb, ...);
SyncFunc<MTE3_S>();

7.4 为什么这套实现能保证正确

  • 地址有效：dst 来自 WindowIn(proxyRank)，与方案 A 用的是同一个地址，只是写入方式不同；
  • 顺序有效：payload 的每个 tile 都以 MTE3_S 收尾，之后才写 flag，因此对端看到 flag 时载荷必然已落地；
  • 接收不变：对端仍是 Wait(flag) + cacheReadInvalidate，不区分数据是网卡搬来的还是核搬来的；
  • 可回退：只需 DirectWindowWrite() 返回 false 并恢复 host 侧门控，即可在支持 AIV 引擎的平台上切回方案 A。

8. 算法与拓扑不变：本地聚合仍然保留

方案 B 只替换搬运指令。notify 的 14 个阶段、通信拓扑、聚合语义全部不变：

阶段做什么方案 B 是否改变
Cleanup / InitPlanHeader清理窗口、写计划头否
BuildLocalRoutePlanParallel按 token 路由构建本地计划否
ReduceLocalCounts本地计数归并否
PlanOutboundPayloads计算跨节点出向载荷否
PublishCountControls（stage 6）把“发往目标 server 的包数 + 各专家人数”写到 proxyRank = target*rps + rankInServer（目标 server 的同号卡）仅搬运方式
AggregateServerCounts（stage 7）等各 sourceServer 的 flag 到齐 → 在本节点聚合成 owner 卡所需表 → 写回本 server 各卡窗口否（聚合逻辑原样保留）
ApplyProxyAggregatesToOwner / FanoutBaseAckSlicesToProxies / WaitAllBaseAckSlices应用聚合结果、扇出 ack 分片、等待回齐否
AssembleBaseAcksAtProxies / PublishBaseAcksFromProxies（stage 12）组装并回传 base ack仅搬运方式
ApplyAllReturnedRowBases应用回传的 row base否
要点：“聚合”是 stage 7 的语义，与传输方式解耦。方案 B 不需要删除任何聚合步骤——所谓“本节点聚合后发对端”的模式仍然成立，只是“发”的动作改成了写窗口。

9. 代价、风险与验证方法

9.1 代价

项说明影响
同步性发送期间占用本核 MTE3，不是异步提交控制面（百字节级）几乎无感
分块拷贝大 payload 需按 tile 循环dispatch/combine 若走同方案，可能需要调大 tile 或多核并行
