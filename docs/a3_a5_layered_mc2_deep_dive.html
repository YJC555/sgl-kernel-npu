0.1 硬件与存储

名词解释在这份代码里
AI Core Ascend 芯片上真正做矩阵/向量计算的核。一个芯片里有很多个，按类型分为 AIC（Cube，做矩阵乘）和 AIV（Vector，做向量/标量搬运）。 tiling 里的 aivNum = platform.GetCoreNumAiv()，以及 SetBlockDim(aivNum)。
AIV AI Vector Core，向量核。它除了算向量，还能执行 DataCopy 这类搬运指令，也能跑我们 kernel 里的标量循环（AscendC 允许在 AIV 上执行标量代码）。 notify kernel 就是纯 AIV 算子；发 WQE、敲 doorbell 也都由 AIV 完成。
AICPU 芯片上的通用标量核（ARM 架构的 CPU 核），不算矩阵，专门跑控制面：协议栈、任务调度、内存注册、状态机。它不是 AI Core，不参与算子主体计算。 A3 上 HCCL 的通信控制面跑在 AICPU 上；kernel 侧通过 Hccl<HCCL_SERVER_TYPE_AICPU> 与它交互。详见第 8 章。
HBM / GM HBM 是芯片外的高带宽显存；在 AscendC 里统一叫 GM（Global Memory）。kernel 的输入输出、通信窗口都在 GM。 GM_ADDR、__gm__ 指针、GlobalTensor。
UB Unified Buffer，AIV 旁边的片上高速缓存，容量很小（百 KB 级）。所有 DataCopy 都要经过 UB 中转，且必须按 32B 对齐。 tiling 里检查 totalUbSize >= REQUIRED_NOTIFY_UB_BYTES；kernel 里 pipe.InitBuffer(...) 申请 UB。
HCCS 华为私有的芯片间高速互联，用于同一台机器/超节点内的卡间通信，带宽高、延迟低，可直接访存。 机内（同 server）的窗口读写走 HCCS；WindowIn(rank) 在机内是直连地址。
RoCE RDMA over Converged Ethernet，把 RDMA 语义跑在以太网/融合网上。跨机通信走它。需要 QP、rkey、WQE 这些 RDMA 概念。 A3 跨机 PostRdmaSend 发 WQE；A5 用 hcomm 的 roce 对象。
UBoE 类似 RoCE，但底层跑在华为 UB（Unified Bus）网络上。A5 上可能有 roce / uboe 两种协议可选。 A5 的 CamMoeLayeredCommContext.protocol；kernel 里 roce_.Init / uboe_.Init 二选一。

0.2 通信与网络

名词解释在这份代码里
HCCL Huawei Collective Communication Library，昇腾的集合通信库（对标 NCCL）。提供 AllReduce / AllGather / AlltoAll / BatchWrite 等原语，负责建链、建 QP、注册窗口。 所有 MC2 tiling 配置、HcclAiRMAInfo、HcclChannel 都来自它。
rank 通信域里的一张卡（一个进程）的编号。epRankId = 本卡编号，epWorldSize = 总卡数。 32 卡双机时 world=32、ranksPerServer=16、rankInServer=rank%16。
server 一台机器（一个节点）。serverNum = world / ranksPerServer。 双机场景 serverNum=2。
集合通信 所有 rank 一起参与、有固定算法的通信，如 AllReduce、AlltoAll。数据面由 HCCL 内部执行，AIV 一般只负责喂数据。 opType=8（AlltoAll）属于这一类。
单边通信 / RDMA Write 一方直接把数据写到对端内存，对端不需要参与（不需要收指令）。需要 QP + rkey。 opType=18（BatchWrite）属于这一类；PostRdmaSend 就是手写一个 RDMA Write WQE。
AlltoAll 每张卡向所有卡各发一份不同数据。MoE 的 dispatch 本质就是 AlltoAll 的一种稀疏形式。 本仓库 notify tiling 目前写的 opType=8。
BatchWrite HCCL 的批量单边写原语。HCCL 会为每个目的 rank 准备发送队列（QP/SQ/WQ）和远端内存描述表，正好是 AIV 自己拼 WQE 所需的素材。 参考实现 opType=18，这正是能拿到 QP 表的关键。
QP Queue Pair，RDMA 的队列对，由 SQ（发送队列）+ RQ（接收队列）组成。一张卡到每个目的 rank 至少一个 QP。 HcclAiRMAInfo.qpNum、sqPtr、按 dstRank*qpNum 寻址。
WQ / WQE Work Queue / Work Queue Entry。WQE 就是“一条发送指令”，里面写清楚：操作类型（写）、长度、远端地址、rkey、本地地址。 PostRdmaSend 里手工填的 hns_roce_rc_sq_wqe。
doorbell “门铃”。把 WQE 填好后，写一个 doorbell 寄存器通知网卡来取活。不敲 doorbell，网卡不知道有新 WQE。 db = qp->wqn | ((head%65536)<<32) | (qp->sl<<48)，然后 DataCopyPad 到 qp->dbAddr。
rkey / lkey 远端/本地内存注册后拿到的“钥匙”。WQE 里必须带 rkey，网卡才允许写对端那块内存（安全 + 地址翻译）。 MemDetails1.key，分 REMOTE_INPUT / LOCAL_OUTPUT 两类。
window（窗口） HCCL 预先注册好的一块 GM 区域，每张卡都有一份，且每张卡都能拿到对端窗口的地址。窗口地址不是普通本地地址，访问它时底层会自动路由：机内走 HCCS、跨机走 RoCE。 WindowIn(rank)、localWindowsIn、remoteRes[rank].windowsIn。
fullmesh 全连接拓扑：每个 rank 与对端所有 rank 都建链。 BatchWrite=level1:fullmesh（非分层跨机）。
hierarchy（分层） 分层拓扑：先机内、再机间，且机间只连“对端同号卡”。32 卡时每卡只有 1 条跨机链路。 BatchWrite=level1:hierarchy（layered 的正确选择）。
pairwise 两两配对。常用于机间只连一个对端的场景。 本仓库现在写的 AlltoAll=level0:fullmesh;level1:pairwise。
layered（分层通信） 一种 MoE 通信方案：跨机只发给“同号卡”，由同号卡在本机内二次分发。好处是把跨机链路数从 O(N) 降到 O(1)，代价是多一跳本地转发。 本仓库 notify_dispatch_normal_layered 与参考仓库 ..._a2_layered.h。

名词解释在这份代码里
MC2 “融合算子”形态：把计算（MatMul/通信）和集合通信放进同一个算子，由 HCCL 参与调度，减少一次 kernel 启动与一次数据落盘。 op 注册时 this->MC2().HcclGroup("comm_group")。

1背景：MoE、layered 与 notify 算子

1.1 MoE 的 dispatch / combine 为什么是通信问题

MoE（Mixture of Experts）模型里，每个 token 只激活少数几个专家。专家分布在不同的卡上，所以要先做一次 dispatch：把 token 按路由结果发到对应专家的卡；专家算完后再做一次 combine：把结果按原路送回。这两步本质都是“不等长的 All-to-All”。

问题在于：如果每张卡都直接和对端所有卡建链（fullmesh），32 卡时每卡要维护 16 条跨机链路，交换机压力和建链开销都很大。于是有了 layered（分层）。

1.2 layered 的核心：跨机只走同号卡

把 rank 按机器分组：rankInServer = rank % ranksPerServer，serverId = rank / ranksPerServer。分层方案规定：

  • 跨机时，本机第 i 号卡只发给对端第 i 号卡（同号卡），一条链路；
  • 到达对端后，由同号卡在本机内再分发给本机其他卡（走 HCCS，快）。

这就是代码里的寻址公式：

// 目标 server 的同号卡
const uint32_t proxyRank = target * info_.ranksPerServer + info_.rankInServer;

当 target 遍历 0..serverNum-1 时，proxyRank 分别等于本机同号卡、对端同号卡……所以“跨机只连一条、机内全连”是写死在寻址里的。

1.3 notify 算子在做什么：14 个 stage

notify 不搬 token 本体，它只同步“元数据”：每个 server 要发多少 packet、每个专家要收多少 member、行号基址是多少。它跑完，dispatch/combine 才知道该往哪写。

Process() 里每个 stage 之间都有一次全核同步（StageBoundary），因此“最后一个打印出来的 stage 号”就直接指明卡死位置。

1.4 故障现象与定位方法

A3 双机跑起来后，日志停在 stage 6：走 PublishCountControls 的 AIV 核里，跨机那一支在 PostRdmaSend 第一句就空指针退出；另一部分核在 StageBoundary(7) 的 SyncAll 等它，于是全体挂死。

定位手法（也是后面自查同类问题的方法）：

  • 按核过滤打点：只让 AIV0/AIV1 打 [ln]，避免每核缓冲把关键日志挤掉；
  • 零解引用探针：只读指针值、不解引用，例如 LoadQpDesc，这样即使 QP 表坏了也能打印出 info=0；
  • host trace：[ln-host] 双写 stderr 与 /tmp/deepep_layered_host.log，用来判断异常发生在 host 建上下文阶段还是 kernel 里。

最终拿到的关键证据就一条：[ln] qp dst=31 info=0 num=0 —— aiRMAInfo 是空指针。

2tiling 阶段到底在做什么（重点）

你说还没接触过 tiling，这一章就从“为什么需要它”讲起，再到普通算子例子、再到 MC2 多了什么，最后讲它和 QP 表的关系。看完应该能独立读懂 notify_dispatch_normal_layered_tiling.cc。

2.1 为什么必须有 tiling：三条硬约束

GPU 的 CUDA kernel 里，线程块大小、共享内存大小是“运行时由你写代码决定”的；Ascend 不完全一样：算子编译时就要确定“用多少核、每核处理哪一段、片上内存怎么切”，这些决策在 host 侧做完，产物就是 TilingData。原因有三个：

  1. 并行度必须提前定：一个芯片有多少 AIV 是平台属性，kernel 里 GetBlockIdx() 只能知道“我是第几号核”，但“一共开了几个核、每个核负责哪段数据”必须由 host 通过 SetBlockDim + TilingData 告诉它。
  2. 片上内存极小：UB 只有百 KB 级，且要求 32B 对齐。一次能搬多少元素、要不要分块（tile）、每块多大，必须在 host 算好，否则 kernel 里现算既慢又容易越界。这也是“tiling（切砖）”这个名字的由来。
  3. kernel 不能动态申请资源：workspace 大小、UB buffer 布局、循环次数，都要在编译/下发前确定。kernel 里只能按 TilingData 里的数字去 InitBuffer、去循环。
一句话 tiling = 在 host 上把“硬件资源 + 输入形状”翻译成“kernel 能直接执行的数字”，写进一个共享结构体。

2.2 一个普通 AscendC 算子的 tiling 长什么样

先把 MC2 的部分拿掉，看最小骨架。下面是一个假想的“逐元素加”算子的 tiling：

// 1) host 与 kernel 共享的结构体（放在 op_kernel/*.h，两边都 include）
struct AddTilingData {
    uint32_t totalElements;   // 一共多少元素
    uint32_t tileElements;    // 每个 tile 多少元素（受 UB 限制）
    uint32_t coreNum;         // 用了几个 AIV
};

// 2) host tiling 函数
ge::graphStatus AddTiling(gert::TilingContext* c) {
    auto* d = c->GetTilingData<AddTilingData>();   // 拿到要填的结构体
    auto platform = platform_ascendc::PlatformAscendC(c->GetPlatformInfo());
    uint32_t aivNum = platform.GetCoreNumAiv();          // 平台有几个 AIV
    uint64_t ubSize = 0;
    platform.GetCoreMemSize(platform_ascendc::CoreMemType::UB, ubSize);

    uint64_t total = c->GetInputShape(0)->GetStorageShape().GetShapeSize();
    d->coreNum     = aivNum;
    d->tileElements = (ubSize / sizeof(float) / 2U) / 32U * 32U; // 留一半、32 对齐
    d->totalElements = total;

    c->SetBlockDim(aivNum);        // 启动 aivNum 个 block
    c->SetTilingKey(1U);          // 选择 kernel 分支
    c->GetWorkspaceSizes(1)[0] = 0;  // 不需要 workspace
    return ge::GRAPH_SUCCESS;
}

// 3) kernel 侧读取
extern "C" __global__ __aicore__ void add(GM_ADDR x, GM_ADDR y, GM_ADDR tiling) {
    GET_TILING_DATA_WITH_STRUCT(AddTilingData, data, tiling); // 解出结构体
    if (TILING_KEY_IS(1)) { /* 用 data.tileElements 分块处理 */ }
}

要点：

  • GetTilingData<T>() 返回的是“已经被框架分配好、等着你填”的结构体指针，不是让你 new 一个。
  • SetBlockDim / SetTilingKey / workspace 都是 host 侧一次性声明的“启动参数”。
  • 结构体必须放共享头文件，host/kernel 各 include 同一份。这是第 2.4 节要讲的 ABI 契约。

2.3 本仓库 notify 的 tiling 实际做了什么

把 NotifyTiling 拆成四段看：

(1) 校验输入与拓扑

const int64_t world = Attr(c, WORLD), rank = Attr(c, RANK), ranks = Attr(c, RANKS), ...
OP_TILING_CHECK(!d || !Shape2D(s, bs, k) || ... || world % ranks || world / ranks > MAX_SERVERS ...,
                OP_LOGE(n, "invalid normal layered notify inputs or topology"), return GRAPH_FAILED);

tiling 是唯一能在“下发前”拦住非法参数的地方。比如 world % ranks 必须为 0（每机卡数整除），否则后面的 rankInServer 寻址就错了。这类检查放在 host 上，失败会直接报错，不会把一个坏 kernel 发到设备上挂死。

(2) 算各种 stride 与 offset（“切砖”的核心）

// 专家前缀表、packet 槽位、recordStride、partialStride、window 布局……
const uint64_t prefixBytes = CamMoeLayered::AlignUp64(expertsU * sizeof(int32_t)) + ...
OP_TILING_CHECK(prefixBytes > SHARED_WORK_UB_BYTES / 2U,
                OP_LOGE(n, "normal layered notify prefix table exceeds UB capacity"), ...);
...
auto w = CamMoeLayered::MakeWindowLayout(...);
OP_TILING_CHECK(... !CamMoeLayeredHost::ValidWindowCapacity(w, Mc2TilingUtils::GetMaxWindowSize()) ...,
                OP_LOGE(n, "normal layered window layout or HCCL buffer capacity is invalid ..."), ...);

这一段看起来很“算术”，但每一行都对应 kernel 里的一次 DataCopy 或一个数组下标。tiling 的错误往往不是“算错一个数”这么简单，而是算出的布局超出了 UB/窗口容量，所以这里有大量 FitsUint32 / MulFits / AddFits 防溢出检查。

(3) 填业务字段

auto &l = d->layered;
l.epWorldSize = world;
l.epRankId = rank;
l.ranksPerServer = ranks;
l.serverNum = world / ranks;
l.rankInServer = rank % ranks;
l.aivNum = platform.GetCoreNumAiv();

{

这就是问题的源头 这里声明的是「AlltoAll + AIV 引擎」。HCCL 收到这个意图后，按集合通信准备资源，不会给 AIV 准备单边写的 QP 表，所以 aiRMAInfo 保持 0。第 6 章会给出正确写法。

2.4 TilingData 是 host 与 kernel 的 ABI 契约

“ABI”听起来很重，其实就一句话：host 往内存里按字段顺序写，kernel 按同样的字段顺序读。所以有三条铁律：

  1. 同一份头文件。host 的 .cc 和 kernel 的 .cpp 必须 include 同一个 *_tiling.h，不能各写一份“看起来一样”的结构体。
  2. 不能随便加字段。在中间插入一个字段，后面所有字段的偏移都会变 —— 而 kernel 是按旧偏移读的，结果就是“地址里全是垃圾”。
  3. TilingKey 分支必须声明。kernel 入口 TILING_KEY_IS(23) 让编译器生成对应 funcEntry；如果 host 设了 23 而 kernel 没声明，实际跑的是 key-0 的默认入口，可能什么都不做。
// 共享结构体：op_kernel/notify_dispatch_normal_layered_tiling.h
struct NotifyDispatchNormalLayeredTilingData {
    Mc2InitTiling mc2InitTiling;   // HCCL 初始化配置
    Mc2CcTiling   mc2CcTiling;     // HCCL 通信算法配置
    LayeredInfo   layered;         // 业务字段（rank、stride、offset…）
};

// kernel 入口
REGISTER_TILING_DEFAULT(NotifyDispatchNormalLayeredTilingData);
if (TILING_KEY_IS(23)) {
    GET_TILING_DATA_WITH_STRUCT(NotifyDispatchNormalLayeredTilingData, data, tiling);
    ...
}

补充一个容易踩的坑：kernel 里 GET_TILING_DATA_WITH_STRUCT 需要一块 UB 暂存区，它通过 GetTPipePtr() 找。所以 TPipe pipe; 必须写在它之前（本仓库代码里就专门留了注释说明这一点，否则会出现 507035 这类“标量访问越界”的错）。

2.5 MC2 比普通算子多了什么

普通算子的 TilingData 只有业务字段。MC2 多了两个不透明（opaque）的通信配置块：

字段内容谁生成谁消费
mc2InitTiling通信域初始化信息（rank、world、buffer 等）HCCL tiling 库（host 调 GetTiling）kernel 内 Hccl 客户端 InitV2
mc2CcTiling通信原语 + 算法（opType + algConfig）同上kernel 内 Hccl 客户端 SetCcTilingV2

关键认知：这两个块不是我们定义的，里面的字段也不该由我们解析。host 只负责“把意图（group/opType/algConfig）告诉 HCCL 的 tiling 库，把产物搬进 TilingData”；kernel 只负责“把产物交给 Hccl 客户端”。中间怎么编码是 HCCL 的内部实现。

也正因为如此，Mc2CcTilingConfig 的三个入参就是全部“沟通语言”：

Mc2CcTilingConfig(group, opType, algConfig)
参数含义写错会怎样
group通信域名（通常来自 op 属性，如 "comm_group"）找不到通信域，tiling 直接失败或 kernel 初始化失败
opType通信原语编号：8=AlltoAll、18=BatchWrite…建错资源类型：用 8 时 HCCL 不准备 QP 表，aiRMAInfo 为 0
algConfig算法/拓扑：原语=level0:拓扑;level1:拓扑建错链路：fullmesh 时每卡连对端所有卡，与 layered 的“同号卡”寻址不符

2.6 两个 setter：SetCommEngine 与 SetAicpuBlockDim

SetCommEngine(AIV_ENGINE)

告诉 HCCL：“这次通信的数据面由 AIV 直接驱动”。在 A5 上这是正确的，因为 950 的 HCCL 真的提供 COMM_ENGINE_AIV。在 A3 上这个声明本身不一定报错，但 A3 的 HCCL 没有对应的 AIV 引擎后端，等到 kernel 侧去取引擎上下文时就会失败（第 5 章有实测 HCCL_E_PARA(1)）。

SetAicpuBlockDim(n)

给 AICPU 侧的通信服务分配多少个“服务核”。参考实现写成：

context->SetAicpuBlockDim(epWorldSize > RANK_NUM_PER_NODE_A2
                         ? mc2tiling::AICPU_NUM_BLOCKS_A2   // 跨机：6
                         : 1);                              // 单机：1

为什么跨机要多给？因为跨机时 AICPU 要维护每个对端的 QP、处理更多 KFC 请求、跑更复杂的调度；单机只有机内链路，1 个就够。不设这个值，AICPU 侧没有足够的服务核，通信初始化/调度会不完整。

2.7 tiling 之后：配置怎么变成 QP 表

host tiling填 mc2InitTiling / mc2CcTiling（opType+algConfig）
→
框架把 TilingData 交给 HCCL 参与本次执行
→
HCCL/AICPU按 opType+algConfig 建窗口、建 QP、填内存描述表
→
launch把 op param（含 aiRMAInfo）注入 kernel
→
kernelHccl 客户端 InitV2 + SetCcTilingV2，拿到非 0 的 aiRMAInfo

注意最后一格：光 host 配对还不够，kernel 里必须明确“初始化并登记 CC tiling”。参考实现里就是那两句 InitV2 / SetCcTilingV2。我们现在的 kernel 一句都没有 —— 这解释了为什么即使 host 这边改了，表也可能还是 0。

  • host 与 kernel 是否 include 同一个 tiling 头？字段顺序有没有被改过？
  • SetTilingKey 与 kernel 的 TILING_KEY_IS 是否一致？
  • MC2 的 GetTiling 是否真的执行了、返回值是否检查过？（参考实现里是 OP_TILING_CHECK(GetTiling(...) != 0, ...)）

  • kernel 里 Hccl 客户端初始化（InitV2/SetCcTilingV2）有吗？

4.3 为什么 A5 可以：条件拆开看

三个条件必须同时成立
  1. HCCL 有这个引擎：950 的 HCCL 提供 COMM_ENGINE_AIV，HcclChannelAcquire / HcclEngineCtxCreate 都能成功。
  2. 硬件/驱动允许 AIV 直接驱动通信：950 把通信能力下沉到了 AIV 可调用的 hcomm 接口，AIV 不需要另一个核代劳。
  3. kernel 用了对的东西：读 roceContext，用 hcommHandle，不碰 aiRMAInfo。

反过来说，只要其中一条不成立，这条路径就断。A3 断在第 1 条（没有 AIV 引擎后端）。

5.2 尝试一：把 A5 的“建引擎上下文”搬到 A3（失败）

思路很自然：A5 能 HcclEngineCtxCreate(COMM_ENGINE_AIV)，那 A3 也照做不就行了？实测结果是：

fail step=engine-get code=1      // HcclEngineCtxGet(comm, tag, COMM_ENGINE_AIV, ...) 返回 HCCL_E_PARA
为什么 code=1 很关键 HCCL_E_PARA(1) 是“参数/能力不支持”的硬错误；如果是“还没创建”，会返回 HCCL_E_NOT_FOUND。所以这不是时序问题、也不是 tag 写错，而是 910_93 的 HCCL 根本没有 COMM_ENGINE_AIV 这个后端。

5.3 尝试二：窗口直写（方案 B，已实现）

既然拿不到 QP 表，就绕开它：直接往对端窗口里写。因为窗口地址是 HCCL 注册过的统一虚拟地址，写它时底层会自动路由（机内 HCCS、跨机 RoCE）。

#ifdef __DAV_C310__
    return false;   // A5 继续用 hcomm 通道
#else
    return true;    // A3 所有“发送”改成窗口拷贝
#endif
}

调用点变成：

proxyRank == info_.epRankId || comm_.DirectWindowWrite()
    ? CopyWindowBytes(payload, dst, layout_.controlStride)      // 普通 GM→GM 拷贝
    : comm_.PostRdmaSend(payload, dst, proxyRank, ...);          // A5

Read 侧同理，用 LoadPeerWindow 拿对端窗口地址后直接读。CopyWindowBytes 内部就是 DataCopy 走 PIPE_MTE3，并在前后加 PipeBarrier + cache 维护。

5.4 方案 B 为什么能跨机

关键认知：窗口地址不是“本机物理地址”，而是 HCCL 注册的远端可寻址地址。当你 DataCopy 到 WindowIn(proxyRank) 时：

  • proxyRank 在本机 → 走 HCCS，直接访存；
  • proxyRank 在对端 → 请求被路由到 RoCE 网卡，由网卡完成封装与远端写入；
  • 对端看到的是自己窗口里多了一段数据，不需要参与任何指令。

所以“DataCopy 走的是 RoCE 不是 HCCS”这个疑问的答案是：DataCopy 只是发起方，具体走哪条链路由地址所属的窗口决定，HCCL 已经把这个映射建好了。

5.5 方案 B 的边界

它解决的是“数据面没有 QP 表”，不解决“控制面没有资源”
  • 窗口本身、remoteRes 仍然是 HCCL/AICPU 建的。如果 remoteRes[rank] 为空，窗口地址就是 0（我们曾出现 rank1→17 dst=5280，本质是窗口基址为 0 加了个偏移）。
  • 性能上，每次发送都是一次 MTE3 搬运，没有 WQE 的批量提交与乱序流水，适合 notify 这种小消息控制面，不适合大流量数据面。
  • 顺序语义要靠 flag + cache 维护自己保证（本仓库用单独的 flag 写 + cacheWriteThrough）。

6.3 isLayered ? "BatchWrite=level1:hierarchy" : ... 到底在说什么

algConfig 的语法是 原语=层级:拓扑[;层级:拓扑]：

  • level0 = 机内（server 内）；level1 = 机间（server 间）；
  • fullmesh = 与对端所有 rank 建链；hierarchy = 分层，机间只连同号卡；pairwise = 两两配对。
场景algConfig含义每卡跨机链路（32 卡）
单机 ≤16 卡BatchWrite=level0:fullmesh机内两两直连，不出机0
跨机、非分层BatchWrite=level1:fullmesh每卡与对端所有卡建链16
跨机、分层BatchWrite=level1:hierarchy只与对端同号卡建链1
为什么 layered 必须选 hierarchy 我们的寻址是 proxyRank = target*ranksPerServer + rankInServer，即“只找同号卡”。如果 HCCL 按 fullmesh 建了 16 条链路，不仅浪费，QP 表里“每个 dstRank 一个 QP 组”的布局也可能与我们的 dstRank*qpNum*sizeOfAiRMAWQ 假设不一致。

6.4 为什么 opType 是 18 而不是 8

opType 决定 HCCL 为“哪种通信原语”准备资源：

  • 8 = AlltoAll：集合通信。数据面由 HCCL 内部（AICPU 调度）执行，AIV 只提供输入输出。HCCL 没有理由把发送队列暴露给 AIV，所以不填 aiRMAInfo。
  • 18 = BatchWrite：批量单边写。AIV 要自己发 WQE，HCCL 就必须把每个目的 rank 的 QP/SQ/WQ 与远端内存描述表交出来，于是 aiRMAInfo 非 0。

一句话：你告诉 HCCL “我要自己发”，它才给你发件工具；你说“你来发”，它就不给。

  2. 框架把 TilingData 交给 HCCL，HCCL 在 AICPU 侧按 BatchWrite 建 QP、建内存描述表；
  3. kernel launch 时，op param 里预留了 aiRMAInfo 字段（此时可能还是 0）；
  4. kernel 调 InitV2：Hccl 客户端向 AICPU 报到，绑定通信域；
  5. kernel 调 SetCcTilingV2(offset)：客户端按该偏移读 mc2CcTiling，把“本次要 BatchWrite”告诉 AICPU 服务，服务把 QP 表地址写回 op param；
  6. 之后再读 aiRMAInfo 就是非 0。

我们现在的代码跳过了第 4、5 步，所以永远停在第 3 步的 0。

8AICPU 到底是什么（重点）

你之前问“AICPU 是什么，我根本不知道”，这一章专门讲清它，以及它为什么在 A3 上不可替代。

8.1 AICPU 在芯片里的位置

一颗 Ascend 训练芯片里通常有三类“处理器”：

类型擅长是否参与算子主体计算
AIC（Cube）矩阵乘是
AIV（Vector）向量运算、搬运（DataCopy）是；我们 notify 就跑在它上面
AICPU通用标量控制流、协议栈、任务调度否，它给 AI Core 打辅助

AICPU 是 ARM 架构的通用核，有自己的指令集，能跑复杂分支、能访问网络设备、能做内存管理。你可以把它理解成“芯片内的一个小 Linux 侧控制面”，专门处理 AI Core 不擅长的杂活。

8.2 为什么通信控制面必须放在 AICPU

RDMA/集合通信的控制面其实非常“重”：

  • 建链：和每个对端交换 QP 信息、协商参数；
  • 内存注册：把窗口地址注册给网卡，换回 rkey/lkey；
  • QP 状态机：RESET → INIT → RTR → RTS，每一步都要按协议改状态；
  • 重传/拥塞/错误处理：分支密集、事件驱动；
  • 集合通信算法调度：Ring/Tree/分层算法要按 rank 计算每一轮发谁收谁。

这些活有两个特点：分支多、要访问外设（网卡）。AIV 是 SIMD 计算核，跑这种控制流效率极低，而且通常不能直接操作网卡寄存器。所以 A3 的设计是：控制面交给 AICPU，数据面交给 AIV。

8.3 KFC：AIV 与 AICPU 怎么协作

KFC = Kernel Function Call。可以把它类比成“kernel 里的远程过程调用”：

AIV 侧把请求（做什么、参数）写进共享队列
→
AICPU 侧轮询队列，取出请求
→
AICPU 执行建 QP / 注册内存 / 调度通信
→
回写结果把状态/地址写回共享内存

所以 Hccl<HCCL_SERVER_TYPE_AICPU> 的语义是：“我要用的 HCCL 服务端在 AICPU 上”。kernel 里调 InitV2 / SetCcTilingV2 时，实际是通过 KFC 把请求投给 AICPU，AICPU 干完活把 QP 表地址写回 op param。

一句话区分 AICPU 是“谁在建资源、维护状态”；KFC 是“AIV 怎么把请求交给 AICPU”的通道。二者是“角色”与“机制”的关系。

所以“A3 上 AIV 能发 RDMA”这句话要加限定：AIV 能发 WQE，但 QP 必须由 AICPU 先建好。AIV 不是独立通信实体。

8.5 A5 为什么可以不要 AICPU 参与

950 的演进方向是“把通信能力做成 AIV 可直接调用的引擎”：HCCL 提供 COMM_ENGINE_AIV，配套 HcclChannelAcquire / HcclEngineCtxCreate 与 hcomm 的 Init/WriteNbi。对 kernel 来说，通信变成了“拿句柄、调函数”，不需要理解 QP 表，也不需要 KFC 往返。

为什么 950 能做到？可以从三个层面理解：

  • 硬件：通信引擎的暴露方式更贴近 AIV，AIV 可以直接驱动；
  • 软件：HCCL 把建链/注册封装进 EngineCtx，host 一次建好，device 直接用；
  • 接口：hcomm 把底层差异吃掉，kernel 只看到 channel 与 write。

于是 A5 的代码形态完全不同：不用 QP 表、不用 HcclOpResParam，用一份引擎上下文。

8.6 “A5 用 AICPU 行不行 / A3 用 AIV 行不行”

组合可行性原因
A5 + AIV 引擎可行（现状）COMM_ENGINE_AIV 真实存在，hcomm 可用
A5 + AICPU/KFC取决于 HCCL 版本；不是首选950 的推荐路径是 AIV 引擎；KFC 是给老架构的兼容路径，是否保留看版本
A3 + AIV 引擎不可行实测 HcclEngineCtxGet(COMM_ENGINE_AIV) 返回 HCCL_E_PARA(1)：没有这个后端
A3 + AICPU/KFC可行（参考实现）arch22 用 Hccl<AICPU> + MC2 CC-Tiling，正常拿到 QP 表
结论 不是“A3 天生没有 QP 表”，而是 “用哪套后端”由平台 + HCCL 版本共同决定。A3 的正确后端是 AICPU/KFC，A5 的正确后端是 AIV 引擎。把 A5 的调用硬搬到 A3，等于用错后端，报参数错误是必然的。

8.7 A3 能不能彻底绕开 AICPU

如果只追求“数据面能通”，方案 B（窗口直写）确实绕开了 QP 表。但要注意：窗口本身、remoteRes 映射仍然是 HCCL 在 AICPU 侧建好的。也就是说：

  • 数据面：可以绕开 QP 表（用窗口拷贝）；
  • 控制面：绕不开 HCCL 的资源建立，只是不经过 KFC 的“发 WQE”环节。

这也是为什么方案 B 仍然要求 remoteRes[rank] 有效。彻底不要 HCCL 只适用于“自己写驱动 + 自己建 QP”的场景，不在算子层做。

9.2 寻址：为什么是 dstRank*qpNum*sizeOfAiRMAWQ

HCCL 把所有目的 rank 的 WQ 连续排在一块 GM 里：第 0 个 rank 占 qpNum 个 WQ，每个 WQ 大小 sizeOfAiRMAWQ。所以第 dstRank 个 rank 的第一组 WQ 就在 dstRank * qpNum * sizeOfAiRMAWQ 处。这个布局与参考实现完全一致，说明我们的寻址假设没错。

9.4 为什么到处是 cacheWriteThrough / cacheReadInvalidate

AIV 访问 GM 时并不保证与其他核/网卡看到同一份缓存。WQE、head/tail、flag 都是多生产者/多消费者共享的数据，所以：

  • 写 WQE 后要 cacheWriteThrough，确保网卡读到的是新内容；
  • 读 tail/flag 前要 cacheReadInvalidate，避免读到自己的旧缓存；
  • 关键步骤之间加 PipeBarrier<PIPE_ALL>，防止编译器/硬件乱序。

这也是方案 B 必须“payload 与 flag 分开写、分开 barrier”的原因：否则接收侧可能先看到 flag、再看到旧 payload。

9.5 为什么写窗口地址也能跨机生效

windowsIn 不是普通 HBM 地址，而是 HCCL 注册窗口的统一虚拟地址。对它的访问由底层传输路由：

  • 同 server → HCCS 直接访存；
  • 跨 server → RoCE，网卡完成封装。

所以方案 B（直接 DataCopy 到窗口）和方案 A（发 WQE）物理上都过 RoCE，区别只是“谁提单”：前者由 AIV 的搬运引擎发起，后者由 AIV 驱动网卡 SQ。

10五维总结：为什么 A5 可以、A3 必须 AICPU

10.1 硬件维度

A3 的通信控制面放在 AICPU（通用核），AIV 只做计算与搬运；A5 把通信引擎下沉到 AIV 可直接调用的位置。这不是“谁更强”，而是两代芯片的通信架构不同。

10.2 HCCL 实现/版本维度

A3 的 HCCL 对外暴露的是 MC2 CC-Tiling + KFC / OpResCtx；A5 暴露的是 Channel + EngineCtx（COMM_ENGINE_AIV）。同一份“建通信资源”的需求，两代走了不同 API。A3 上调 HcclEngineCtxGet(COMM_ENGINE_AIV) 返回 HCCL_E_PARA，是最直接的证据。

10.3 资源模型维度

10.4 kernel ABI 维度

A5 的第一个入参是 roceContext（host 建好的上下文）；A3 必须靠 GetHcclContext 拿 op param，并调用 InitV2/SetCcTilingV2 完成与 AICPU 的握手。入参不同、初始化不同，代码不能直接复用。

10.5 性能与适用场景维度

  • QP 表 + WQE：批量提交、乱序流水、单边写，适合大数据量；notify 这种控制面小消息用它反而“杀鸡用牛刀”，但语义最标准。
  • 窗口直写：实现最简单，每次一次 MTE3 搬运，适合小消息；大流量时 CPU 侧循环与 cache 维护成本高。
  • hcomm channel：A5 的推荐路径，兼顾易用与性能。

10.6 反向问题：为什么不能“一套代码通吃”

因为两代平台的 能力集不同：

  • A3 没有 COMM_ENGINE_AIV 后端 → A5 路径在 A3 上第一步就失败；
  • A5 的推荐路径不需要 QP 表 → 硬塞 A3 的 WQE 代码没有意义；
  • 唯一能“通吃”的是窗口直写，因为它只依赖窗口地址，而窗口两边都有。但它的代价是性能与 remoteRes 依赖。

所以合理设计是：按平台编译分支（正是本仓库用 __DAV_C310__ 做的事），A5 走 hcomm，A3 走 MC2 CC-Tiling + QP 表（主攻）或窗口直写（保底）。
