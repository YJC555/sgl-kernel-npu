sgl-kernel-npu 结构解析

照着目录读代码

这个仓库到底在做什么

它是 DeepEP 的昇腾（Ascend NPU）移植版：给 MoE（混合专家）模型做“把 token 分发给各卡上的专家，再把结果收回来”的通信库。

仓库里有两条产品线，别混在一起看：

  • DeepEP 线（python/deep_ep + csrc/deepep）：本文档的重点，做 dispatch / combine / 低延迟 / 融合。
  • 通用算子线（python/sgl_kernel_npu、python/attentions）：RMSNorm、SwiGLU、注意力、FLA、Mamba、采样等推理算子，与 MoE 通信无直接关系。
A2 / A3 / A5 三种卡各自有实现 Python 门面 → C++ 桥接 → AscendC 算子 算子卡片可点击展开

3. python/deep_ep：用户能感知的入口

这一层只做“决策和转发”，真正的通信与搬运都在 C++/kernel 里。

python/deep_ep/deep_ep/buffer.py入口最常改

作用用户唯一需要的“句柄”。构造时创建 C++ runtime（拓扑 + HCCL 通信域），并按 DEEP_USE_MODE 一次性建好 normal / low_latency / fused 三套策略；对外暴露 get_dispatch_layout、dispatch、combine、low_latency_dispatch/combine、融合接口。

关键点

  • num_nvl_bytes / num_rdma_bytes 只被保存，不参与实际分配；真正的窗口大小由 HCCL_BUFFSIZE 决定。
  • get_dispatch_config 对 2/4/8 卡返回 (num_sms, x, 256, 6, 128)；num_sms 后面推出 num_channels = num_sms / 2。
  • 真正决定走哪套策略的是构造时的环境变量，而不是每次调用时判断。

向上提供

dispatch / combine / layout / 低延迟 / 融合

向下依赖

deep_ep_cpp.Buffer（C++ 实现）+ 策略对象
python/deep_ep/deep_ep/ep_strategy.py策略

作用定义策略基类与注册表，以及 StrategyMap——把环境变量 DEEP_USE_MODE 映射成 (normal 策略, low_latency 策略) 的组合。

DEEP_USE_MODEnormal 策略low_latency 策略
defaultdefaultdefault
alltoallalltoallalltoall
opsdefaultops

关键点register_*_strategy 装饰器把实现注册进字典，get_*_strategy(name) 按名字取类。新增算法只需加一个带装饰器的类。

strategies/normal_strategy.py策略A2/A3/A5 共用

作用normal 模式的两套实现：DefaultNormalCommStrategy（自定义算子，主力）与 AllToAllNormalCommStrategy（标准集合通信）。

关键点

  • get_num_rdma_ranks() > 1 时走 _internode_dispatch，否则走 _intranode_dispatch——这是“单机/多机”的分叉点。
  • 多机分支只支持 BF16/FP16，量化会直接报错。
  • dispatch 返回后组装 handle（8 元组），combine 只真正用到其中 4 项。
strategies/low_latency_strategy.py策略

作用低延迟模式实现。default 走 deep_ep_cpp 的 moe_distribute_*_v2；ops 走 torch_npu 自带算子；alltoall 走集合通信。

关键点

  • OpsLowLatencyCommStrategy 会先把输入 padding 到 num_max_dispatch_tokens_per_rank，并维护 x_active_mask。
  • comm_alg 支持 hierarchy / fullmesh_v1 / fullmesh_v2 / ccu——这才是“fullmesh”的真实出处。
  • 量化模式支持 int8 / mx_fp8 / pertoken_fp8 / mx_fp4（A5 才全支持）。
strategies/fused_strategy.py策略

作用把“dispatch + 专家计算 + combine”压进一个融合算子的三种形态：fused_deep_moe、dispatch_ffn_combine、mega_moe。

关键点融合模式跳过 Python 层的来回调度，适合固定形状的 decode 场景；对应 FuseMode 枚举 1/2/3。

python/deep_ep/deep_ep/utils.py
EventOverlap（把 event 包装成可等待对象）、log_parameters（打印调用参数）、_resolve_quant_mode（把布尔开关查表成量化模式字符串）等通用工具。
python/deep_ep/deep_ep/device_info.py
读取 SoC 型号并查 QUANT_MODE_TABLE：2201 → A2/A3；9301 / 9201 / 3510 → A5。决定“同一份代码在哪种卡上能用哪些量化模式”。
python/deep_ep/deep_ep/strategies/__init__.py
导入三个策略模块，触发所有 @register_*_strategy 装饰器执行——没有这一步，注册表是空的。

4. csrc/deepep：Python 与算子之间的桥

csrc/deepep/deep_ep.cpp核心

作用C++ 层 Buffer 的实现。构造时确定拓扑（单机 8 卡分组、多机 layered 部署、A5 分层上下文）、拿到 HCCL 通信域名、算好轮次参数；调用时把 Python 传入的张量整理成算子要求的形态，再依次调用 notify / dispatch / combine 的 aclnn 接口。

构造阶段

rank/device 绑定 · SoC 判断 · HCCL comm name · LayeredCommContext

调用阶段

张量校验 · int64→int32 · 分配中间张量 · 下发算子

关键点

  • get_dispatch_layout 与 intranode_dispatch 是两条独立链路：前者只算布局，不通信。
  • num_tokens 不是参数，来自 x.size(0)；num_experts 才是显式业务参数。
  • 三个 prefix_matrix 用 at::empty 分配后从未写入，是兼容占位。
csrc/deepep/pybind_extension.cpp
pybind11 绑定：把 Buffer 的方法和 Config 暴露给 Python。这里能看到 Config 的默认值（num_sms=20 等）。
csrc/deepep/config.hpp / config.cpp
Config 结构定义与缓冲区大小提示函数。注意本移植版里 get_nvl_buffer_size_hint 基本是空壳，直接返回 hidden 字节数。

5. AscendC 算子的三层结构（先看这个再读算子）

每个算子都由“定义 + tiling + aclnn 封装 + kernel”四部分组成，分布在两个目录。

层位置干什么
算子定义op_host/<op>.cpp声明输入/输出/属性，注册 SoC 版本，写 InferShape / InferDataType
Tilingop_host/<op>_tiling.cchost 侧算切分参数、校验显存、算 workspace、选 tiling key
aclnn 封装op_host/op_api/aclnn_<op>.cpp两段式接口：GetWorkspaceSize 跑 tiling → Execute 下发
Kernel 入口op_kernel/<op>.cpp按 TILING_KEY_IS 选模板，每核各跑一份
Kernel 主体op_kernel/<op>.h真正的搬数据、算前缀、写窗口
共享 tiling 结构op_kernel/<op>_tiling.hhost 写、kernel 读的“契约结构体”
A2 与 A3/A5 的关系：ops/ 编译给 A3/A5（部分文件用 __DAV_C310__ 区分），ops2/ 编译给 A2。同名算子往往有两份实现，读代码时先确认自己在哪套构建里。

6. 算子卡片（A3 / A5，ops/）

点击标题展开：作用、输入输出、实现要点、三卡差异。

dispatch_layoutA3A5A2 有独立版

作用只读 topk_idx，算出三张布局表：每个 rank 收多少 token、每个专家收多少 token、哪些 token 要去哪个 rank。不通信，是 dispatch 前的一次“本地统计”。

输入 / 输出输入 topk_idx（int64，形状 [num_tokens, topk]）；输出 5 个 int32 张量（num_tokens_per_rank、num_tokens_per_rdma_rank、num_tokens_per_expert、is_token_in_rank 等）。

实现要点

  • 多核按 token 分片，每个核先统计自己那部分，再用 atomic 累加到全局计数。
  • 需要两遍扫描：第一遍计数，第二遍按前缀生成槽号（send_token_idx_small）。
  • A2 版走 dispatch_layout_a2.h，多机时还涉及 serverNum 与稠密槽位。

文件op_host/dispatch_layout.cpp、op_host/dispatch_layout_tiling.cc、op_kernel/dispatch_layout.cpp/.h、op_api/aclnn_dispatch_layout.cpp

notify_dispatchA3A5元数据交换

作用把“本地各专家要收多少”广播给所有 rank，并据此算出三类偏移表：专家段起点（send_data_offset）、每个 (专家, 源rank) 的接收起点、以及轮次偏移。它只搬元数据，不搬 token 数据。

输出（关键）

send_data_offset · recv_count · recv_offset
expert_global_offset · srcrank_in_expert_offset · r_in_srcrank_offset

下游谁用

dispatch 用 send_data_offset 定写入槽号；
combine / 重排用另三张表定输出行号

实现要点内部按“核的职责”分工：有的核做 all-gather 计数，有的核做前缀和，有的核负责超时等待与状态标记。A3/A5 用 notify_dispatch.h，A5 还有 notify_dispatch_a5.h；分层部署走 notify_dispatch_normal_layered.*。

文件op_host/notify_dispatch.cpp、notify_dispatch_tiling.cc、op_kernel/notify_dispatch.cpp/.h、op_api/aclnn_notify_dispatch.cpp

cam_moe_dispatch_normalA3A5主力算子

作用真正的 token 搬运：把本 rank 的 token 按 topk 结果写进目标 rank 的窗口，再按“专家优先”的布局从各源窗口拉回来，形成 expand_x。

输入 / 输出输入 x、topk_idx，加上 layout 与 notify 的 6 张表；输出 expand_x（重排后的 token）、dynamic_scales（量化 scale）、expand_idx（三元组逆置换表）、recv_count 等。

实现要点

  • 窗口地址 = 基址 + 双缓冲半区 + 保护带偏移 + 槽号 × 512B 槽长。
  • 每个 512B 槽内是 [hidden][32B scale][12B 三元组]，三元组记录 (源rank, 源token, k)。
  • 输出行号 = 专家段起点 + 专家内按源 rank 的偏移 + 轮次偏移，三张表相加，不做排序。
  • A5 版 cam_moe_dispatch_normal_a5.h 只换了窗口基址与保护带常量；分层部署走 *_layered.*。

Tiling key13000（无量化）/ 13002（int8）/ A5 的 15000、15002~15005（对应不同 fp8/fp4 模式）。

文件op_host/cam_moe_dispatch_normal.cpp、..._tiling.cc、op_kernel/cam_moe_dispatch_normal.cpp/.h/_a5.h、op_api/aclnn_cam_moe_dispatch_normal.cpp

cam_moe_combine_normalA3A5回程

作用把专家算完的结果按三元组送回原 token：每个 expand 行送回 (源rank, 源token, k) 对应的位置，乘 topk_weights[k] 后累加，得到 combined_x。

实现要点

  • 入口参数很少（x + topk + src_idx + send_head），因为布局信息全在 dispatch 阶段算好了。
  • 多轮长序列走 cam_moe_combine_normal_multi_round.h。
  • A5 版 ..._a5.h 的差异同样集中在窗口基址与状态区。

文件op_kernel/cam_moe_combine_normal.cpp/.h/_a5.h/_multi_round.h、op_host/cam_moe_combine_normal_tiling.cc、op_api/aclnn_cam_moe_combine_normal.cpp

moe_distribute_dispatch_v2 / combine_v2A3A5低延迟

作用低延迟模式的 dispatch / combine 实现，面向 decode 场景的小批量、低时延通信。走的是另一套窗口寻址与状态协议，不经过 normal 的三元组表。

实现要点

  • 变体齐全：_a5.h（A5 专项）、_ccu.h（CCU 卸载）、_layered.h（分层部署）、_single.h（单机）。
  • 入口文件 moe_low_latency_dispatch_v2.cpp / moe_low_latency_combine_v2.cpp。
  • 量化模式由 Python 层先转成整数（0/2/3）再传入。
fused_deep_moeA3A5融合

作用把 dispatch + 专家 FFN 计算 + combine 合成一个大算子，减少 kernel 启动与中间结果的 GM 往返。

实现要点kernel 主体在 fused_deep_moe_base.h，A5 有专门目录 fused_deep_moe_a5/；tiling 需要额外传入专家权重、量化参数。

dispatch_ffn_combine融合

作用另一种融合形态：dispatch 之后直接接 FFN（两个专家矩阵乘 + 激活），再 combine。适合固定 batch 的推理。

实现要点kernel 主体拆在 dispatch_ffn_combine_kernel/ 子目录，按阶段分文件；tiling 结构与普通 dispatch 不同，需要携带 FFN 的 shape 与权重布局。

op_kernel/common.h / data_copy.h / comm_args.h / sync_collectives.h
公共基础设施：对齐与类型宏、GM↔UB 的 DataCopyPad 封装、通信参数常量、跨核/跨 rank 同步原语。几乎所有 kernel 都间接依赖它们。
op_kernel/check_winsize.h / moe_distribute_base.h / quantize_functions.h
窗口容量自检、低延迟通信基类、量化/反量化函数模板（int8、fp8、fp4 的转换与 scale 处理）。
op_kernel/cam_moe_layered_comm.h / *_layered_tiling.h
分层部署（Layered）专用：多机按 server 分层的通信实现与 tiling 契约。对应环境变量 DEEPEP_LAYERED_RANKS_PER_SERVER、DEEPEP_LAYERED_PROTOCAL（roce / uboe）。

7. 算子卡片（A2，ops2/）

A2 的算子目录结构相同，但实现细节显著不同：窗口偏移固定 210MB、没有 hybrid 分支、多机需要 serverNum。

dispatch_layout（ops2）A2

作用与 A3/A5 版同职责，但 kernel 在 dispatch_layout_a2.h 中实现，多机路径要考虑 server 维度与稠密槽位。

差异tiling key 区间不同（约 23 / 123）；A2 把“专家优先”编号直接放在 GM 上，减少 UB 中转。

notify_dispatch / notify_dispatch_a2A2

作用A2 的元数据交换。除了常规计数广播，还要处理 serverNum 维度，并在窗口内划分 notify 专用的 202MB 区域。

实现要点notify_dispatch_a2.cpp/.h 是 A2 专项实现；tiling 在 notify_dispatch_tiling_a2.cc；aclnn 入口 aclnn_notify_dispatch_a2.cpp。

cam_moe_dispatch_normal（ops2） / dispatch_normal_a2A2

作用A2 的 token 搬运主体。

关键差异

  • 窗口基址：GetWindowsInAddr + 8MB + 202MB，无 hybrid 判断。
  • 双缓冲半区 = (总窗口 - 8MB) / 2；状态区在窗口末尾。
  • 槽号计算与 A3/A5 相同：sendOffset[专家] + 段内序号。
  • dispatch_normal_a2.cpp 是另一条多机路径，支持 layered 变体。
cam_moe_combine_normal（ops2） / moe_distribute_combine_a2A2

作用A2 的回程与低延迟回程。文件与 A3/A5 同名，实现按 A2 的窗口布局改写；moe_distribute_combine_a2_layered.h 支持分层部署。

ops2/op_host/tiling_args.h / mc2_tiling_utils.h
A2 专用常量与 tiling 工具：COMBINE_STATE_WIN_OFFSET = 8MB、NOTIFY_DISPATCH_BUFF_OFFSET = 202MB，以及窗口大小校验函数。
