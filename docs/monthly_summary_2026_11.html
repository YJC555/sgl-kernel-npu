一、本月内容完成情况

1. A3 双机分层通信挂死问题：从定位到解决

问题现象

A3 双机 32 卡运行 layered dispatch 时，notify 算子在 stage 6/7 挂死：主节点 AIV0 能走完 701→703→704→702→stage7，AIV1 只到 701；从节点现象相反；其余核卡在 StageBoundary(7) 的 SyncAll，双机互等。

定位过程

① 建立可观测性

在 14 个阶段埋入 TracePoint（stage*100+step 编码），增加按核过滤（仅 AIV0/AIV1）、窗口关系快照，以及“零解引用”的 QP 探针，避免探针本身空指针 trap。

② 排除误判

初期“某些关键点不打印”被证实是 kernel printf 每核缓冲保尾丢头、以及落盘非时间序，而非代码未执行，避免了错误方向。

③ 锁定直接原因

日志显示窗口侧完全正常（ctx peer win=0x80000000），唯一缺口是 aiRMAInfo = 0——MC2 算子 op param 里没有 AI-RMA 的 QP 表。跨节点发送核在 PostRdmaSend 第一句 rdmaInfo_->qpNum 处空指针退出。

④ 追到下发点

QP 表并非仓库代码写入，而是 HCCL 在 AIV 引擎上下文建立后填充。按 A5 相同逻辑在 A3 执行后，HcclEngineCtxGet(..., COMM_ENGINE_AIV, ...) 返回 HCCL_E_PARA(1)，确认 A3(910_93) 的 HCCL 不提供该引擎，无法下发 QP 表。

解决方案

方面内容
思路不再让 AIV 核拼 RoCE WQE，改为直接写 WindowIn(peer) 窗口地址 + flag（方案 B）
改动stage 6 与 stage 12 的 4 处跨节点发送点；接收侧 Wait(flag) + cacheReadInvalidate 零改动
兼容A5 路径完全不受影响；保留开关，未来 A3 支持 AIV 引擎时可低成本切回
文档结论整理为技术说明，推送至 readme 分支供评审
方案 B 保持算法与通信拓扑不变：14 个阶段、本地聚合（stage 7）、server 内扇出、ack 回传全部保留，只替换“最后一公里”的搬运指令。

二、个人成长机会

  1. 调试方法论升级：从“看日志猜原因”转向“提出可验证假设 → 最小插桩 → 二分定位”。本次把失败步骤写进异常消息（step=...），一次就锁定了 HCCL 调用位置。
  2. 通信机制理解：理清 HCCL 两条数据面路径（AIV 直接提单 vs 窗口地址写），理解了“地址即通信语义”的设计，而不只是会改一处代码。
  3. 跨平台差异意识：不再假设“A5 能跑的 A3 也能跑”，先建立平台能力矩阵、再用最小实验验证边界。
  4. 工程表达：把技术结论组织成可评审文档（现状、根因、方案对比、代价与回退），提升汇报与横向协作效率。
待提升：底层源码不可见，部分结论依赖实测推断；当前仅完成功能验证，性能（直写 vs 单边写）尚未量化；对 A5 全链路掌握仍偏浅。

三、周边资源

  • 平台与环境：双机 32 卡真实环境与脚本化重编重跑流程，是本次定位的前提。
  • 代码参照：仓库既有 A3 非分层实现（dispatch/combine v2 系列）为“窗口直写”提供同源佐证，避免从零摸索。
  • 接口文档：CANN/HCCL 返回码语义（HCCL_E_PARA 与 HCCL_E_NOT_FOUND 的差异）是判定“平台不支持”而非“未初始化”的关键依据。

四、心得体会

1. 现象不等于原因

前期最大的弯路，是把“日志没打出来”当成“代码没执行”，实际是 printf 缓冲与落盘顺序问题。先分清“没执行 / 没打印 / 打丢了”，才能不误判。

2. 先定位层级，再动代码

问题可能出在 kernel、host 或平台能力三层。本次在 host 侧用一条 step= 就证明了是平台能力缺失，避免了在 kernel 里做无效改造。

3. 尽早验证能力边界

一个 API 的返回码可以省下几天的试错。遇到“上游应该会给我们数据”的假设，应第一时间用最小实验证伪或证实。

4. 改动要留可回退开关

方案 B 把差异收敛到 DirectWindowWrite() 一个判断，既保住 A5 原有路径，也让未来平台能力补齐后能低成本切回。

5. 文档化是能力的放大器

把定位过程、方案取舍与代价写清楚，不仅方便汇报，也让同类问题下次能直接复用结论，而不是重新踩一遍。
