1问题回顾：为什么 stage 6 会挂死

notify 算子的 Process() 一共 14 个 stage，每两个之间有一次全核同步。stage 6 的 PublishCountControls() 负责把 CountControl 发给“对端同号卡”：

// notify_dispatch_normal_layered.cpp（改动前）
const uint32_t proxyRank = target * info_.ranksPerServer + info_.rankInServer;
if (proxyRank == info_.epRankId || comm_.DirectWindowWrite()) {
    CopyWindowBytes(payload, dst, layout_.controlStride);        // 窗口直写（方案 B）
} else {
    comm_.PostRdmaSend(payload, dst, proxyRank, layout_.controlStride, *doorbell_, *head_);
}

注意这三个版本的区别：分支第一版（81454d1 a5 layered init，即最初克隆/初始化后的版本，upstream main 里还没有这个文件）里没有 DirectWindowWrite()，发送分支是 if (proxyRank == info_.epRankId) Copy else PostRdmaSend，所以 A3 跨机必然走右边 → 空指针。后来方案 B（6f10fc4）才加入 DirectWindowWrite() 并让 A3 恒为 true，于是走左边。本次改造（4489078）把它改成“有 QP 表就走 PostRdmaSend，没有才回退”。第一版的代码是：

// 81454d1（分支第一版）
if (proxyRank == info_.epRankId) {
    CopyWindowBytes(payload, dst, layout_.controlStride);
} else {
    comm_.PostRdmaSend(payload, dst, proxyRank, layout_.controlStride, *doorbell_, *head_);
}

当时的 PostRdmaSend 第一句就是：

// PostRdmaSend 的第一句
auto qpNum = rdmaInfo_->qpNum;   // rdmaInfo_ == nullptr → 该核直接退出

跨机那一支空指针退出，其余核卡在 StageBoundary(7) 的 SyncAll 等它，全体挂死。定位探针打印出的关键证据只有一条：

[ln] qp dst=31 info=0 num=0
根因不是“A3 没有 QP 能力” 而是我们的算子从来没有向 HCCL 声明“我要自己发单边写”，也没有在 kernel 里完成 CC-Tiling 登记。HCCL 因此没有准备 QP 表，HcclOpParam::aiRMAInfo 保持为 0。

本次改造就是把这条链路补齐，让 aiRMAInfo 变成非 0，从而用回 PostRdmaSend，不再依赖窗口直写。

3改动前：我们的三处做法与三个缺口

3.1 host：声明成了“集合通信 + AIV 引擎”

// notify_dispatch_normal_layered_tiling.cc（改动前）
void SetComm(NotifyDispatchNormalLayeredTilingData *d, const std::string &g)
{
    AscendC::Mc2CcTilingConfig c(g, 8U, "AlltoAll=level0:fullmesh;level1:pairwise");
    c.SetCommEngine(mc2tiling::AIV_ENGINE);
    c.GetTiling(d->mc2InitTiling);
    c.GetTiling(d->mc2CcTiling);
}
// 调用处
SetComm(d, std::string(g));
// 没有 SetAicpuBlockDim

问题有两层：

  • opType=8（AlltoAll）：集合通信由 HCCL 内部完成，它没有理由把发送队列交给 AIV，所以不会填 aiRMAInfo。
  • SetCommEngine(AIV_ENGINE)：这是 A5 的配法。A3 没有 COMM_ENGINE_AIV 后端，这个声明不会让 HCCL 去建 QP。

3.2 kernel：只读表，不登记

// notify_dispatch_normal_layered.cpp（改动前，入口）
GET_TILING_DATA_WITH_STRUCT(NotifyDispatchNormalLayeredTilingData, data, tiling);
// 没有任何 Hccl 初始化
...
op.Process();

3.3 CommAdapter：直接当成“没有表”

// cam_moe_layered_comm.h（改动前）
rdmaInfo_ = (__gm__ HcclAiRMAInfo *)context_->aiRMAInfo;
...
__aicore__ inline bool DirectWindowWrite() const
{

这里把 A3 写死成方案 B。它掩盖了 QP 表缺失的问题，也让我们无法验证“表是否真的下发了”。

4改动后：四份文件的具体修改

4.1 host tiling：按平台分支

// notify_dispatch_normal_layered_tiling.cc（改动后）
void SetComm(NotifyDispatchNormalLayeredTilingData *d, const std::string &g, bool crossServer)
{
#ifdef __DAV_C310__
    (void)crossServer;
    // A5(950)：HCCL 提供 AIV 通信引擎，保持 AlltoAll 声明，不需要 QP 表
    AscendC::Mc2CcTilingConfig c(g, 8U, "AlltoAll=level0:fullmesh;level1:pairwise");
    c.SetCommEngine(mc2tiling::AIV_ENGINE);
    c.GetTiling(d->mc2InitTiling);
    c.GetTiling(d->mc2CcTiling);
#else
    // A3(910_93)：只有单边批量写才下发 QP 表；分层跨机只连同号卡 → hierarchy
    const std::string algConfig =
        crossServer ? "BatchWrite=level1:hierarchy" : "BatchWrite=level0:fullmesh";
    AscendC::Mc2CcTilingConfig c(g, 18U, algConfig);
    c.GetTiling(d->mc2InitTiling);
    c.GetTiling(d->mc2CcTiling);
#endif
}

// 调用处
SetComm(d, std::string(g), servers > 1U);
#ifndef __DAV_C310__
c->SetAicpuBlockDim(servers > 1U ? mc2tiling::AICPU_NUM_BLOCKS_A2 : 1U);
#endif

三点说明：

  • 用 #ifdef __DAV_C310__ 而不是运行时判断 SoC：该文件本来就用这个宏区分 A5/A3 的 UB 预算（HCOMM_UB_BYTES），说明 host 侧是按目标 SoC 分别编译的，沿用它最一致。
  • 单机退回 level0:fullmesh：单机不存在跨机层，用 level0 全连接即可；跨机才有 hierarchy 的意义。
  • 不保留 SetCommEngine(AIV_ENGINE)：A3 没有这个后端，保留只会造成误导。

4.2 kernel：补齐 InitV2 / SetCcTilingV2 / Finalize

// notify_dispatch_normal_layered.cpp（改动后，入口）
GET_TILING_DATA_WITH_STRUCT(NotifyDispatchNormalLayeredTilingData, data, tiling);
#ifndef __DAV_C310__
// A3：控制面在 AICPU。InitV2 绑定通信域，SetCcTilingV2 把 mc2CcTiling
// 交给 AICPU 服务；正是这一步让 HCCL 把 QP 表写进 aiRMAInfo。
auto contextGM0 = AscendC::GetHcclContext<AscendC::HCCL_GROUP_ID_0>();
Hccl<HCCL_SERVER_TYPE_AICPU> hccl;
hccl.InitV2(contextGM0, &data);
hccl.SetCcTilingV2(offsetof(NotifyDispatchNormalLayeredTilingData, mc2CcTiling));
#endif
...

#ifndef __DAV_C310__
hccl.Finalize();
#endif

同时加了 #include <cstddef> 以使用 offsetof。

4.3 CommAdapter：从“写死方案 B”改成“有表用表”

// cam_moe_layered_comm.h（改动后）
rdmaInfo_ = (__gm__ HcclAiRMAInfo *)context_->aiRMAInfo;
// 只有 HCCL 真正下发了 QP 表才走 PostRdmaSend；否则回退窗口拷贝
directWindowWrite_ = (rdmaInfo_ == nullptr || rdmaInfo_->qpNum == 0U);

__aicore__ inline bool DirectWindowWrite() const
{
#ifdef __DAV_C310__
    return false;
#else
    return directWindowWrite_;
#endif
}

新增成员：bool directWindowWrite_{true};（仅 A3 分支）。这样 notify 在表下发后自动走 PostRdmaSend，不再使用方案 B；而尚未迁移的 dispatch/combine 仍能安全回退。

4.4 deep_ep.cpp：只更新注释

没有改逻辑（A5 仍创建引擎上下文、A3 仍跳过），只把“A3 用窗口直写”的旧注释改成“A3 走 MC2 CC-Tiling”。

5按执行顺序走一遍：每一步谁做了什么

① host tilingSetComm：A3 写 BatchWrite + hierarchy；SetAicpuBlockDim(6/1)
→
② 框架/HCCL按 BatchWrite 建窗口、QP、内存描述表
→
③ launchop param 注入 kernel（aiRMAInfo 此刻可能仍为 0）
→
④ kernel InitV2绑定通信域，读 mc2InitTiling
→
⑤ SetCcTilingV2AICPU 按 mc2CcTiling 初始化并回填 QP 表
→
⑥ CommAdapter::Init读到非 0 表 → directWindowWrite_=false
→
⑦ stage 6/12PostRdmaSend 正常拼 WQE 发送
→
⑧ Finalize释放 AICPU 侧客户端

5.1 关于第 ③ 步“表还可能为 0”

QP 表不是 host 在 launch 前填好的，而是 kernel 完成登记后由 AICPU 回填。所以顺序必须是：先 InitV2 + SetCcTilingV2，再让 CommAdapter::Init 去读 aiRMAInfo。这也是为什么我们把初始化放在 op.Init(...) 之前、GET_TILING_DATA 之后。

5.2 关于第 ⑤ 步为什么必须传 offset

kernel 里 tilingData 的设备地址在 host 侧不可知，但 mc2CcTiling 相对结构体开头的偏移是编译期常量。HCCL 用 (char*)&tilingData + offset 定位，因此接口设计成 offsetof。

5.3 关于第 ⑥ 步的判定

我们没有直接把 A3 写死成“用 QP”，而是用 rdmaInfo_ == nullptr || qpNum == 0 判定。好处是：

  • notify 表下发成功 → 走 WQE；
  • 任何还没迁移的算子 → 自动回退，不会空指针崩溃；
  • 现场排查时，只要看 DirectWindowWrite() 的实际分支就能知道表有没有下发。

6为什么改之前不行（三个层面）

6.1 语义层面：AlltoAll ≠ 单边写

opType 是给 HCCL 的“资源类型声明”。AlltoAll 是集合通信，HCCL 自己执行数据面，AIV 不需要发送队列；BatchWrite 是单边批量写，AIV 要自己发 WQE，HCCL 才必须把 SQ/WQ 与远端内存描述交出来。声明错，资源就不会被创建。

6.2 接口层面：A5 的 EngineCtx 在 A3 不存在

我们曾尝试照搬 A5 的 HcclEngineCtxGet(comm, tag, COMM_ENGINE_AIV, ...)，实测返回 HCCL_E_PARA(1)。这个错误码是“参数/能力不支持”，而不是“尚未创建”（那会是 HCCL_E_NOT_FOUND）。说明 A3 的 HCCL 根本没有这个后端。

6.3 时序层面：kernel 不登记，表永远不会出现

即使 host 已经按 BatchWrite 建好资源，只要 kernel 不调 SetCcTilingV2，HCCL 客户端就不知道“本次用哪套 CC 配置”，也就不会把 QP 表地址写回 op param。host 声明与 kernel 登记是一对，缺一不可。

为什么“改成窗口直写”能临时绕过，但不是正解 方案 B 只是绕开数据面的 QP 表，控制面（窗口、remoteRes）仍由 HCCL/AICPU 建立；而且它掩盖了“声明与登记缺失”这个真问题。现在按 arch22 补齐后，我们才真正用上单边写能力。

7为什么改之后可以（四条因果链）

7.1 host 声明对了，HCCL 才会准备 QP

opType=18 + BatchWrite=level1:hierarchy 告诉 HCCL：“这是单边批量写，跨机只连同号卡”。HCCL 据此为每个可达目的 rank 建 QP、注册远端内存、生成 QP 表。

7.2 AICPU 服务核够了，跨机调度才完整

SetAicpuBlockDim(6) 给 AICPU 侧通信服务分配 6 个服务核。跨机要维护更多 QP、处理更多 KFC 请求，单核不够；单机退回 1 个，避免浪费。

7.3 kernel 登记了，表才会被回填

InitV2 把 op param 与 TilingData 交给 Hccl 客户端；SetCcTilingV2(offset) 让客户端按偏移读取 mc2CcTiling，向 AICPU 发起初始化。AICPU 完成后把 QP 表地址写入 aiRMAInfo，qpNum > 0。

7.4 判定与发送对上了

CommAdapter::Init 读到非 0 表 → directWindowWrite_ = false → 远程发送走 PostRdmaSend。WQE 布局（dstRank*qpNum*sizeOfAiRMAWQ）与 arch22 完全一致，所以不需要改发送代码。

因果闭环 声明（host）→ 建资源（HCCL/AICPU）→ 登记（kernel）→ 回填表（AICPU）→ 判定（CommAdapter）→ 发送（PostRdmaSend）。六个环节现在都通了。

9A5 为什么完全不受影响

维度A5（__DAV_C310__）A3（else）

10.4 失败时的排查顺序

  1. 若 info 仍为 0：确认 host tiling 真的走了 A3 分支（宏/SoC 编译）、GetTiling 是否成功、kernel 是否进了 TILING_KEY_IS(23)；
  2. 若 info 非 0 但 num=0：多半是 algConfig 与拓扑不匹配（hierarchy 只连对端同号卡，检查 ranksPerServer 属性）；
  3. 若发送仍失败：检查 PostRdmaSend 的 rkey 表（memPtr 的 REMOTE_INPUT）与目的窗口偏移是否一致。

10.5 回退

若 A3 现场需要临时保底，把 directWindowWrite_ 初值改回 true 即可恢复方案 B；host tiling 的 BatchWrite 声明可以保留（它不影响窗口直写）。
