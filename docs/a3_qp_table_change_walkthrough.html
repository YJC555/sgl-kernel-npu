0. 结论速览

  • 第一版（81454d1）把 A3 当成 A5 写：host 用 AlltoAll + AIV_ENGINE 声明通信，kernel 从不登记 CC-Tiling。HCCL 因此不会为 A3 准备单边写资源，aiRMAInfo 恒为 0。
  • 本次改造只做一件事：把“声明 → 登记”这条 MC2 流程补齐，让 HCCL 在 AICPU 上建好传输并回填 QP 表。发送代码本身第一版就写好了，改前只是拿不到表。
  • host 三件事：opType=18（BatchWrite）、algConfig=level1:hierarchy / level0:fullmesh、SetAicpuBlockDim(6 / 1)。出处：arch22 host L130–136 / L784 / L792–810。
  • kernel 两件事：Hccl<HCCL_SERVER_TYPE_AICPU> + InitV2 + SetCcTilingV2(offsetof(...))，结束时 Finalize()。出处：arch22 kernel L285 / L291–303 / L1587。
  • A5 保持 AlltoAll + AIV_ENGINE 不变：A5 的通信走 adv_api/hcomm 通道，不读 aiRMAInfo，强行改成 BatchWrite 反而破坏现有路径。

1. QP 表到底是什么

aiRMAInfo 是 HCCL 放在 HcclOpParam（group 0 的通信上下文）里的一个指针，指向一张“单边写资源表”。字段与用途：

字段含义在发送时怎么用
qpNum每个目的 rank 分配了几个 QP地址步长 = qpNum × sizeOfAiRMAWQ
sqPtrSend Queue 数组首地址按目的 rank 偏移后得到 HcclAiRMAWQ
sizeOfAiRMAWQ单个 WQ 结构大小与 qpNum 一起算 strided 下标
memPtr每个 rank 的内存描述数组取 REMOTE_INPUT 的 rkey、LOCAL_OUTPUT 的 lkey
sizeOfAiRMAMem单个内存描述大小同上，算 memPtr 的步长
curRankId当前 rank调试/校验用
关键认识：这张表不是 host 填的，也不是算子自己填的。它由 HCCL 在 AICPU 侧根据 host 的 CC-Tiling 声明创建传输后写回。算子能做的只有两件事：声明清楚要什么通信（host），把声明登记给 HCCL（kernel）。

3. 执行顺序：一次 kernel 从 tiling 到发送

host：NotifyTiling() ├─ 校验属性 / 计算窗口与 plan 布局 ├─ SetComm(d, group, crossServer) ← 改动 1：声明 BatchWrite ├─ SetAicpuBlockDim(6 / 1) ← 改动 2：分配 AICPU 控制面 ├─ SetBlockDim(aivNum) / SetTilingKey(23) └─ 把 mc2InitTiling / mc2CcTiling 写进 TilingData device：kernel funcEntry（TILING_KEY_IS(23)） ├─ GET_TILING_DATA_WITH_STRUCT(...) ├─ contextGM0 = GetHcclContext<HCCL_GROUP_ID_0>() ├─ Hccl<HCCL_SERVER_TYPE_AICPU> hccl ├─ hccl.InitV2(contextGM0, &data) ← 改动 4：绑定通信域 ├─ hccl.SetCcTilingV2(offsetof(..., mc2CcTiling)) ← 改动 4：登记通信参数 │ └─ HCCL 在 AICPU 建传输，把 sqPtr/qpNum/memPtr 回填进 aiRMAInfo ├─ op.Init(...) │ └─ CommAdapter::Init: rdmaInfo_ = context_->aiRMAInfo ← 改动 5 ├─ op.Process() │ └─ stage 6: PostRdmaSend 读 qpNum/sqPtr/memPtr，写 WQE 并 ring doorbell ← 改动 6 └─ hccl.Finalize() ← 改动 4：释放 AICPU 客户端

4. 改动 1：host SetComm 声明 BatchWrite

4.1 第一版（81454d1）怎么写的

// 81454d1: csrc/deepep/ops/op_host/notify_dispatch_normal_layered_tiling.cc（节选）
AscendC::Mc2CcTilingConfig c(g, 8U, "AlltoAll=level0:fullmesh;level1:pairwise");
c.SetCommEngine(mc2tiling::AIV_ENGINE);
c.GetTiling(d->mc2InitTiling);
c.GetTiling(d->mc2CcTiling);

这套写法是给 A5 准备的：A5 有 AIV 通信引擎，AlltoAll 声明即可。A3 上用它会出两个问题：

  • 8U（AlltoAll）不是单边写语义，HCCL 不导出 SQ/QP；
  • AIV_ENGINE 在 A3 不存在，HCCL 直接返回 HCCL_E_PARA(1)（这就是之前 fail step=engine-get code=1 的来源）。

4.2 现在（4489078）

4.3 逐行作用

行内容作用 / 不加会怎样
L91crossServer ? "BatchWrite=level1:hierarchy" : "BatchWrite=level0:fullmesh" level0=机内、level1=跨机；hierarchy 表示分层，只连对端同号卡。fullmesh 会要求两两建链，跨 16+16 卡时资源对不上，layered 拓扑也不需要。
L92Mc2CcTilingConfig c(g, 18U, algConfig) 18U 是 HCCL_CMD_BATCH_WRITE。只有这个 opType 才会让 HCCL 准备“单边写”资源并导出 QP 表。用 8U（AlltoAll）拿不到。
L93–94GetTiling(d->mc2InitTiling) / GetTiling(d->mc2CcTiling) 分别生成初始化阶段和通信阶段参数，写进 TilingData。kernel 侧要靠这两块登记，缺一块 HCCL 无法建传输。
—不调用 SetCommEngine A3 默认就是 AICPU 上的 CC 引擎；显式指定 AIV 引擎会返回 HCCL_E_PARA(1)。

5. 改动 2：host SetAicpuBlockDim

// csrc/deepep/ops/op_host/notify_dispatch_normal_layered_tiling.cc  L300–308
SetComm(d, std::string(g), servers > 1U);
#ifndef __DAV_C310__
    // A3 的通信控制面在 AICPU：跨机需要完整的 AICPU 服务块，单机 1 个即可
    c->SetAicpuBlockDim(servers > 1U ? mc2tiling::AICPU_NUM_BLOCKS_A2 : 1U);
#endif
c->SetBlockDim(l.aivNum);
c->SetScheduleMode(1);

为什么需要
HCCL 的 A3 客户端跑在 AICPU 上。不给 AICPU 分配 block，kernel 里的 InitV2 没有可用的服务进程去执行，QP 表不会有人填。
为什么是 6
AICPU_NUM_BLOCKS_A2 = 6 是 HCCL 跨机场景约定的 AICPU 服务块数量；单机不需要跨机调度，1 个即可。
不加会怎样
典型表现是 info != 0 但 num == 0，或者 head 增长而 tail 不动（队列没人消费）。
与 A5 的区别
A5 没有 AICPU 控制面，这段用 #ifndef __DAV_C310__ 整体跳过。

arch22 出处

                              ? mc2tiling::AICPU_NUM_BLOCKS_A2 : 1);

我们只是把判断条件从“总 rank 数 > 单机卡数”换成“server 数 > 1”，含义相同，都是“是否跨机”。

6. 改动 3：TilingData 与 offsetof 的 ABI

// csrc/deepep/ops/op_kernel/notify_dispatch_normal_layered_tiling.h  L5–9
struct NotifyDispatchNormalLayeredTilingData {
    Mc2InitTiling mc2InitTiling;   // 必须在偏移 0
    Mc2CcTiling mc2CcTiling;       // kernel 用 offsetof 告诉 HCCL
    CamMoeLayeredInfo layered;
};
  • InitV2(contextGM0, &data) 传的是结构体首地址，HCCL 默认从偏移 0 读 mc2InitTiling。所以 mc2InitTiling 必须是第一个成员。
  • SetCcTilingV2(offsetof(..., mc2CcTiling)) 显式告诉 HCCL 第二块在哪。用 offsetof 而不是写死字节数，结构体增删成员时不会错位。
  • host 端写 d->mc2InitTiling / d->mc2CcTiling，kernel 端按同一结构体读，这是 host/device 之间的 ABI 契约。
常见错误：把 mc2CcTiling 放到结构体中间却在 kernel 里写死偏移，或 host 与 kernel 用了两个不同的结构体定义。表现同样是 aiRMAInfo=0 或通信参数乱码。

标记语句作用不加会怎样

9.4 doorbell 位域

位字段来源

为什么取第 0 个 QP：测试创建 Buffer 时 num_qps_per_rank=1，所以 qpNum=1，每个目的 rank 只有一个 QP，我们取该 rank 区块的第一个即唯一一个。若以后调大 num_qps_per_rank，需要按 lane 再分摊，否则多核会抢同一个 SQ。

11. 为什么改前不行、改后可行

11.1 改前：三个层次同时缺失

层次缺什么结果
语义层host 声明的是 AlltoAll（集合通信），不是 BatchWrite（单边写）HCCL 没有理由准备 SQ/QP
接口层kernel 没有 Hccl 客户端，也没有 SetCcTilingV2CC-Tiling 只停留在 TilingData 里，没有交给 HCCL
时序层即使补了声明，若在 op.Init 之后才登记rdmaInfo_ 已缓存为 0，后续无法刷新

失败的直接形态：stage 6 跨机分支走 PostRdmaSend，第一句 rdmaInfo_->qpNum 解引用空指针，该 AIV 退出；另一核在 SyncAll 等待，表现为挂死。方案 B（窗口直写）当时绕过了这里，但已于 17fcc66 移除，不再作为回退路径。

11.2 改后：闭环形成

  1. host 声明 BatchWrite + 分层算法，并分配 AICPU 控制面；
  2. kernel InitV2 绑定通信域，SetCcTilingV2 登记参数；
  3. AICPU 侧 HCCL 建传输，把 qpNum / sqPtr / memPtr 回填进 aiRMAInfo；
  4. CommAdapter::Init 读到有效指针；
  5. PostRdmaSend 用表里的 QP、rkey、lkey 构造 WQE，ring doorbell 完成一次单边写。
因此：发送代码第一版就写对了，真正缺的是“让 HCCL 愿意并且在正确时机把表交出来”。本次改造没有新增发送逻辑，只补齐了声明与登记。

12. A5 为什么保持原样

维度A5（950）A3（910_93）
host 声明AlltoAll + AIV_ENGINE（保持不变）BatchWrite + 默认 AICPU 引擎
kernel 通信adv_api/hcomm + roce_/uboe_ 通道Hccl<AICPU> + AiRMA QP 表
是否读 aiRMAInfo否是（唯一数据面来源）
为什么不能互换A5 没有 AICPU 控制面，用 BatchWrite 反而丢掉 AIV 引擎路径A3 没有 AIV 通信引擎，用 AIV_ENGINE 直接 HCCL_E_PARA

所以 SetComm 里用 #ifdef __DAV_C310__ 分流，是两台机器硬件能力差异的直接映射，不是临时开关。
